# integral-cms

An embeddable CMS for Vite-based frameworks. It runs inside the host app (same repo, same deploy), with no separate service. Status: proof of concept. See README.md for the vision, usage and roadmap.

## Commands

- `pnpm dev:astro` / `dev:nuxt` / `dev:tanstack`: build packages, then run the example (ports 4321 / 3000 / 3100), the core watcher and the admin playground in parallel. Core changes reload in the example without a restart. The playground has HMR on `localhost:5173/admin/` and proxies `/api/cms` to the example (`CMS_URL`). The example's `/admin` uses the admin built at startup; `pnpm --filter @integral-cms/admin watch` rebuilds it on change (full reload)
- `pnpm build`: packages and all examples
- `pnpm typecheck`: runs `build:packages`, then typechecks all workspaces. Run it before calling work done. While a dev watcher runs, use `pnpm -r typecheck` instead (see Gotchas).
- `pnpm build:packages`: required after any change in `packages/*`, because examples consume `dist/`. Core builds first, then the admin writes into `packages/core/dist/admin`
- Core migrations are code in `packages/core/src/db/index.ts`. Add a new key; never edit one that has shipped.
- `pnpm test`: Vitest in `packages/core` (`pnpm --filter integral-cms test:watch` to watch). For one test, run `npx vitest run <file> -t '<name>'` in `packages/core`; `pnpm ... test -- -t` does not filter. No build needed, tests import `src/`.

## Testing

- TDD, RED then GREEN: write a failing test first and run it to see it fail for the right reason. Then write the least code that makes it pass. A bug fix starts with a test that reproduces it.
- Tests live next to the code as `*.test.ts`. Unit tests cover pure functions. `src/app.test.ts` is the integration suite: a real `defineCms()` on `:memory:` libsql, driven through `createClient()` with a `fetch` that calls `cms.fetch` and keeps the session cookie. Add HTTP behavior there.
- Examples and adapters are not tested yet. Verify them with the curl smoke test below.

## Architecture

- `packages/core` publishes as `integral-cms`, with exports `.`, `./client`, `./register` (types only), `./presets`, `./astro`, `./nuxt`, `./vite`, `./admin`, `./admin/vue`, `./admin/react`. It is built with tsdown to `dist/`. `vue`, `react` and `react-dom` are optional peers used only by the two helpers, `vite` only by `./vite`.
  - `src/schema.ts`: field and schema types, type inference (`Data`, `Doc`), `defineCollection()` / `defineGlobal()` identity helpers for `const` inference, `dataSchema(fields, data)` builds the zod validator per write, because conditions depend on the data (a field whose `condition` is false keeps only its type check), `parseData()` runs it and throws `ValidationError` keyed by field path. `checkFields()` runs at startup: conditions MUST name existing fields, `unique` only on top-level fields of allowed types in collections, and every `pattern` compiles. Field options live on `Common` (every field, joins too) and `Base` (stored fields); `FieldArgs` types field hooks and `validate`. Hook types: `CollectionHooks`, `GlobalHooks`, `FieldHooks` (on every field but `join`), `RootHooks`, `Slot` (array or named record), `LocalApi` (the untyped `cms` hooks get). Hook arguments use method syntax (bivariant), so a typed collection is still a `Collection`; with the wide `Fields` (inline in `defineCms`) they are `any`. `defineCollection()` / `defineGlobal()` keep the literal `hooks` type, so a host can omit a record entry by name. `group` nests `Fields`; `filterable()` / `FilterKey` keep groups, joins and `many` relations out of `where`. Read types: `Resolve` types a populated read, `Populate` lists valid `populate` paths, `Select` the valid `select` keys for a populate spec (a wide `number` P, the `ReadOptions` constraint, allows every join), `Selected` narrows a resolved type to the selected keys (`id` kept, plain records pass), `SelectOf` reads `O['select']`, `Exact` rejects extra keys (an object under a `true`-only key is `never`), `Checked` applies both to an options literal (`D` is the default depth, for `PopulateOf`), and `Wide` returns plain records for an untyped schema (the admin's). A `slug` follows `required` like other fields; a value is checked against `SLUG_PATTERN`. `readOnly` is an admin hint only; core never reads it.
  - `src/helpers/` (barrel `index.ts`, re-exported from `.` and `./client`): `slugify.ts` (`slugify()`, `SLUG_PATTERN`; shared with the admin by relative import like `condition.ts`), `seo-meta.ts` (`seoMeta()`) and `breadcrumbs.ts` (`breadcrumbs()`, walks the resolved `parent` chain, no queries). Helpers MUST have no imports, so they run in the browser.
  - `src/presets/` (`integral-cms/presets`, barrel `index.ts`): one file per preset, `page.ts`, `seo.ts`, and `nested-paths.ts` (`nestedPaths()`). Plain field objects and named hook records; each file MUST stay readable without core internals, because it is the documentation of what a host gets. They import only `errors.ts`, `helpers/slugify.ts` and types, so no zod reaches browser bundles. Paths are stored by the `path` hook; `updateChildPaths` re-saves children with `cms.update(collection, id, {})`, so nothing read through `afterRead` is written back.
  - `src/index.ts`: `defineCms({ collections, globals, populate, database, secret, auth, hooks })` returns the local API (`find`, `findOne`, `findById`, `create`, `update`, `delete`, `getGlobal`, `setGlobal`) plus `fetch(request)`. `cms.populate` holds `{ depth, maxDepth }` with defaults; its `depth` type is the config literal, which the client reads. `bind(scope)` builds the local API for a `Scope` (`trx`, `user`, `context`, `nested`); the exported `cms` is `bind()` with no user. Every method goes through `run()`: `beforeOperation` / `afterOperation` (collections only), one transaction for writes (reused when `scope.trx` is set), and `afterError` at the outermost call for unexpected errors. Hooks get `cms: bind(inner scope)`, so nested calls share `trx` and `context`. `write()` is the pipeline of `create`, `update` and `setGlobal` (validation runs twice, around `beforeChange`), `read()` of the find methods (`checkRead()` throws `Invalid select: <path>` before the query; `pick()` runs after `afterRead`, so `afterOperation` sees the selected documents; `getGlobal` does the same), `afterRead()` runs field then collection `afterRead`, `fieldHooks()` walks fields depth-first. `update()` / `setGlobal()` with `effect` skip id checks and `validate` for `onDelete` effects. In `write()`: `fillSlugs()` fills empty slugs from `from` (every write, before `beforeValidate`), `update` and `setGlobal` merge the input over the stored data (top-level keys, from the raw row, so read hooks never leak into it), `applyDefaults()` (create only, before `beforeValidate`), `runValidate()` (after the first validation, collects all messages), `checkUnique()` (after the second validation).
  - `src/relations.ts`: `checkSchema()` (startup checks), `checkRefs()` (ids MUST exist, no self-reference; throws `ValidationError`), `populate()` (resolves relations and joins in place, and runs the target collection's read hooks through `ReadHooks`), `parsePopulate()` (`?populate=` / `?depth=`; returns the spec or the 400 message, which names the path), `pick()` (keeps `id` and the `select` keys; never throws), `checkSelect()` (returns the first bad path; same resolution rules as `populate()`), `parseSelect()` (`?select=`, longer path wins, no schema), and `onDelete()`, which applies `onDelete` after the row is deleted: `restrict` throws, then `set-null` and `cascade` run through the `Effects` callbacks (the local API with hooks). `relationPaths()` finds relations at the top level and in groups.
  - `src/errors.ts`: `ValidationError` (`errors` by field path, HTTP 400) and `ConflictError` (restrict, HTTP 409), exported from `integral-cms`. It MUST have no imports, so browser code can import errors without zod.
  - `src/condition.ts`: `matchCondition()` and the `Condition` type. It MUST have no imports: the admin imports it by relative path and bundles it, like `client.ts`. `schema.ts` imports it, so zod never reaches the admin.
  - `src/client.ts`: `createClient()`, a typed HTTP client for `/api/cms` with the local API's method names. It owns `API_BASE`; core imports it from here, because the file has no runtime dependencies. Imports types only, so it is safe in the browser. Its types come from the `Register` interface; a type argument overrides it. `src/register.d.ts` (copied to `dist`) augments it with the type of `#integral/config`'s default export. If that alias does not resolve, `cms` is silently `any`, so test typing with `@ts-expect-error`. Keep it in sync with the routes in `app.ts`. `Http` / `HttpFields` map the schema to what HTTP sends (private fields optional), also for populated targets; they skip untyped schemas, where the recursion would not terminate. `Collections<C>` / `Globals<C>` export that mapping for the Nuxt composable. `readQuery()` sends `populate` and `select` through `paths()`; `select: {}` goes out as `select=`. The admin uses it too (`packages/admin/src/api.ts`), so it is the only HTTP client.
  - `src/app.ts`: Hono app. `/api/cms/*` has `auth/*` (better-auth) and the public GET read routes (`collections/:name[/:id]`, `globals/:name`; query params are equality filters coerced to the field type, `null` means `IS NULL`, an empty value adds no filter, except `limit`, `populate`, `depth` and `select`; `readOptions()` returns the read options or the 400 message), then CSRF and session middleware, then `schema` (without `hooks` and other functions) and the write routes. `private` is an HTTP rule: `strip()` removes private fields from every public response, recursing into groups, populated relations and joins, and runs on the picked result; `whereFromQuery()` rejects them as filters. Reads look up a session (`readLevel()`) only when a cookie is sent, and a failed lookup counts as public. It does not validate: write routes pass the raw body to `c.var.cms`, the local API bound to the session user by `asUser()`. Every error body has `message`: `onError` maps `ValidationError` to 400 `{ message, errors }`, `ConflictError` to 409 `{ message, references }`, `HTTPException` to its status, anything else to 500 without the real message; `notFound` returns 404 `{ message }`.
  - `src/auth.ts`: `authOptions()` merges the host's `auth` options (better-auth's, without `modelName`) with core's. Core owns `database`, `basePath` and `secret`, forces `emailAndPassword.enabled`, and runs its `user.create.before` hook first: once a user exists, a request without a session cannot create users on any endpoint. Server calls without a request pass.
  - `src/db/`: Kysely over `libsqlDialect(client)`, the hand-written `Database` interface (`cms_documents`, `cms_globals`), and `migrate()`: Kysely's `Migrator` with inline migrations (table `cms_kysely_migration`), then better-auth's `getMigrations()` for auth and plugin tables.
  - Adapters generate no code. They alias `#integral/config` to the host's `integral.config.ts` and point the framework at runtime files that ship as `.ts` source in `dist/` (tsdown `copy`). The host's Vite or Nitro compiles them. `env.d.ts` stubs `#integral/config`, `#app` and `App.Locals` so core can typecheck them; it is not published.
  - `src/admin/`: hand-written `index.d.ts` for `integral-cms/admin` and `default.ts`, the stub `#integral/admin` resolves to when the host has no `integral.admin.ts`. Both are copied to `dist/admin` (with `entry.ts` and `virtual.d.ts`), where the admin's Vite build writes `index.js`. `vue.ts` and `react.ts` are tsdown entries: `renderVue(Component)` / `renderReact(Component)` wrap a host component into a `Mount` with reactive props and `update`.
  - Standalone admin page: `src/admin/entry.ts` mounts the admin with `#integral/admin`, `src/admin/html.ts` builds the page from the entry's script and CSS URLs and holds the helpers all adapters share (`adminPath`, `adminAlias`, `adminInput`, `adminChunk`, `Options`), and `#integral/admin-html` exports that page as a string (`src/admin/virtual.d.ts`, referenced by `register.d.ts`). No host shell, CSS or JS loads on `/admin`.
  - `src/vite/index.ts`: `integralAdmin()` for Vite frameworks without an adapter. Sets `ssr.external` for builds, aliases `#integral/admin`, adds the entry as a second `client` input, and serves `#integral/admin-html` (dev: `server.transformIndexHtml`, so framework preambles like React Refresh get in; build: from the client bundle, which builds before the server).
  - `src/astro/index.ts`: `injectRoute` for `/api/cms/[...path]` with `src/astro/route.ts` and, unless `admin: false`, `<path>/[...path]` with `src/astro/admin.astro` (reads the base from `Astro.routePattern`, imports `../admin/entry.ts`). `addMiddleware` with `src/astro/middleware.ts` (sets `locals.integral`), the Vite alias, `ssr.external`. `injectTypes` augments `App.Locals` and the client's `Register` with `typeof import(entry).default`; it is a string because Astro's API takes a string, and it MUST stay a module (`export {}`), or `declare module` replaces the client's types instead of augmenting them.
  - `src/nuxt/index.ts`: `nuxt.options.alias` (Nuxt forwards it to Nitro and to tsconfig `paths`), `build.transpile` for the runtime dir, `addServerHandler` for `/api/cms/**` with `runtime/server/handler.ts`, unless `admin: false`, a standalone `/admin` page: `dist/admin/entry.ts` is a second client Vite input, `runtime/server/admin.ts` returns the page from the Nitro virtual `#integral/admin-html` (dev: `@vite/client` + `/@fs` path; build: from `build:manifest`, where the entry is also deleted so Nuxt does not preload it on host pages), `addTypeTemplate` references `integral-cms/register` (app and Nitro contexts), `addImports` of `useIntegral` from `runtime/composables.ts` (`useAsyncData` around `createClient()`'s read methods; during SSR the client fetches through `event.fetch`, typed via `import type cms from '#integral/config'` and the client's `Collections` / `Globals`). Adds the libsql native binaries to Nitro's `traceInclude`. `h3` is an optional peer because the handler imports it.
- `packages/admin` is `@integral-cms/admin` (private). It's a Vue 3 + vue-router + Tailwind v4 app built in Vite lib mode to `packages/core/dist/admin/index.js`, with Vue bundled in and the CSS inlined (`?inline`), injected by `mountAdmin()`. The admin always runs on a page of its own, so the global styles stay. `src/index.ts` exports `mountAdmin(el, options, base)` and `defineAdmin()`. Titles go through Unhead (`useHead`, template `<title> · Admin`); host pages get their `label`. `src/options.ts` holds `optionsKey`, `integralKey` and `pagePath()`. Its types come from `packages/core/src/admin/index.d.ts`, the only copy. Options are named slots (`fields` by custom type name, `pages` by key with optional `route`), each a `Mount<Ctx>` function: `(el, ctx) => cleanup | { update?(ctx), unmount() }`. `Mount.vue` runs one, adds `ctx.integral`, and forwards context changes to `update`; `FieldInput.vue` and the router use it. `FieldInput.vue` renders a group as a `<fieldset>` and recurses, gets `siblings` (`{ fields, data }` of the object that holds the field) and `isNew`, which the slug input needs for `from` and the `parent` prefix, disables `readOnly` fields, and shows the message for its `path` from `errors` (the 400 body, set by `DocForm.vue`); `DocForm.vue` `normalize()` shapes initial data and the payload; an empty optional group saves as `null`, plain defaults pre-fill new documents (`isNew`), and a field whose condition is false saves as `null`. `active()` in `api.ts` wraps core's `matchCondition()`; `DocForm.vue` and `FieldInput.vue` (prop `root`) hide inactive fields. `FieldInput.vue` binds the built-in checks as HTML attributes and shows `description`. Host pages are registered before the built-in routes; on an equal path vue-router keeps the first, so a host page on `/` or `/collections/...` replaces the built-in view. `index.html` + `src/main.ts` are the dev playground.
- Hosts customize the admin with `integral.admin.ts` at the project root (`export default defineAdmin({ fields, pages })`). A page's `route` starts with `/` and defaults to `/<key>`. Pages without `label` stay out of the sidebar. Adapters alias `#integral/admin` to it if it exists, else to the stub. Adding or removing it needs a dev server restart.
- All examples: the instance lives in `integral.config.ts` at the project root, collections in `collections/*.ts`. Each has `collections/pages.ts` from the preset and a catch-all route that reads by `path` (`[...path].astro`, `[...path].vue`, `routes/$.tsx`); static routes win over it.
- `examples/astro`: pages use `Astro.locals.integral`; `[...path].astro` reads with `populate` + `select` and renders `breadcrumbs()`. Secrets come via `astro:env`.
- `examples/tanstack-start`: no adapter package. `tsconfig.json` maps `#integral/config` and loads `integral-cms/register` for the client type. The splat server route `src/routes/api/cms/$.ts` calls `cms.fetch`. `integralAdmin()` in `vite.config.ts` (also keeps core external in SSR builds), and `src/routes/admin.$.ts` returns `#integral/admin-html` as a server route. Pages read content through `createServerFn` in loaders (loaders also run on the client). Nitro v3 via `nitro/vite`. Secrets come from `process.env` (`.env` loads in dev and `vite preview`).
- `examples/nuxt`: `integral.config.ts` calls `useRuntimeConfig()` (`NUXT_CMS_SECRET`, `NUXT_DATABASE_URL`); Nitro's auto-import transform covers root files. Pages use `useIntegral()`; there are no hand-written API routes.

## Design decisions

- **One JSON documents table** for all collections. Schema changes need no migration. Filters use `json_extract`, and field names are checked against the schema before they reach SQL. SonicJS does the same.
- **Core owns the fixed tables only.** CMS migrations are hand-written Kysely code in the bundle, so they run without a filesystem (Cloudflare later). better-auth creates its own tables from the actual options, plugins included. All run lazily on the first DB access.
- **Kysely, own libsql dialect.** better-auth's `getMigrations()` only works with its Kysely adapter. `@libsql/kysely-libsql` pulls an older `@libsql/client` and a second native binary that the Nuxt build does not trace, so core has a small dialect over its own client.
- **No module-level state.** Everything lives in the `defineCms()` closure, so several instances can coexist.
- **Lazy DB and auth.** Nothing connects at import time. The secret is checked when auth is first used, so public pages keep working with a bad config.
- **The admin is a compiled library the host bundles.** Core never imports it, so headless is free. Extensions come from `integral.admin.ts`, compiled by the host's Vite with HMR.
- **Extension contract is `mount(el, ctx)` only.** No framework components cross the boundary, so the admin bundles its own Vue and hosts install nothing. Reactivity is by callbacks: `ctx.onChange` in, `update(ctx)` out. New admin slots MUST use `Mount<Ctx>` too. Admin helpers go into `ctx.integral` (`IntegralContext`: `base`, `navigate`), never at the top level of a context.
- **One published package.** Framework adapters are subpath exports with optional peer deps (`astro`, `@nuxt/kit`, `@nuxt/schema`, `h3`, and `vue` / `react` / `react-dom` for the admin helpers).
- **SQLite only for now**, through libsql (a file or Turso). D1 and Postgres come later, behind the same `documents` shape.
- **Admin path is an adapter option** (`admin: '/cms'`, default `/admin`), not part of `integral.config.ts`: routes are registered at build time, before the config can load. `adminPath()` in `src/admin/html.ts` validates it; the page passes it to the admin router as `data-base`. `/api/cms` (`API_BASE`) stays fixed.
- **Relation ids live in the document JSON.** A string, or a string array for `many`. Reverse lookups (joins, delete checks) scan with `json_extract` / `json_each`. Id lists go in as one JSON parameter (`IN (SELECT value FROM json_each(?))`), so there is no variable limit. Populate runs one query per field per hop.
- **Validation and hooks live in the local API.** HTTP is a thin layer, so server code, HTTP and the admin behave the same.
- **Writes run in one transaction** with their hooks, `onDelete` effects and nested calls. Nested calls MUST go through the hook's `cms`.
- **Presets are data, not features.** No `findByPath`: paths are stored and filtered like any field. The SEO title fallback is computed by `seoMeta()` at render time and never stored.
- **Reads are public, writes need a session.** Pages render the content anyway, and the Nuxt composable needs an HTTP read path for client-side navigation. Drafts will have to gate here later.
- **Private is an HTTP rule.** The local API, hooks and the admin see every field. `app.ts` strips private fields from public responses.
- **Options the admin evaluates MUST be JSON.** Conditions, built-in checks and plain defaults run in both places; `validate`, function defaults and hooks run on the server only.

## Gotchas (each cost a debugging round)

- Nitro rewrites `typeof window` to `"undefined"` as plain text, even inside strings. Keep browser-only code out of server bundles.
- libsql loads `@libsql/<platform>` with a dynamic require:
  - If Vite bundles core, the native binding breaks. That's why the Astro adapter and `integralAdmin()` set core as `ssr.external` in builds. Dev does not bundle, so it stays internal there and Vite reloads it.
  - Nitro's tracer misses the binary. That's why the Nuxt module adds `traceInclude`.
- `tsdown --watch` MUST run with `--no-clean`. Otherwise Nitro rebuilds while `dist/` is empty and logs ENOENT errors. Never run `build:packages` while the watcher runs: the core build deletes `dist/` (including `dist/admin`) under the watcher.
- `Object.assign(el, { dataset: ... })` throws: `dataset` is a getter. Use `setAttribute`.
- Nitro v3 (TanStack Start) traces the libsql binary on its own. Nitro 2 (Nuxt) does not.
- TanStack Start streams HTML. Use `grep -a` on curl output, or grep treats it as binary and prints nothing.
- `nuxt preview` runs with cwd `.output/`, so a relative `file:./cms.db` lands in the build output and gets wiped. Use absolute paths; the Nuxt example uses `resolve('cms.db')`.
- Astro 7 `astro dev` / `astro preview` run as daemons. Use `npx astro dev stop`, `npx astro preview logs`.
- `astro preview` does not load `.env`. The script runs it through `node --env-file-if-exists=.env`.
- `astro check` does not detect `@astrojs/check` under Astro 7. Use `astro sync && tsc --noEmit`.
- Nuxt: use `nuxt typecheck`. Plain `vue-tsc --noEmit` with Nuxt's reference-only tsconfig checks nothing.
- `tsc --noEmit` in the Astro example never checks `.astro` frontmatter. To test `App.Locals` typing, use a `.ts` file.
- Nuxt's `.nuxt/types/nitro-routes.d.ts` imports every server handler for `$fetch` route types, and that file belongs to the app tsconfig project. Server runtime files in a module MUST import from `h3`, not `#imports`, or the app project cannot resolve them.
- tsdown `copy` with a directory `from` nests the directory under `to`. Use the parent as `to`.
- A stale Astro daemon or leftover `cms.db` makes sign-up return 403 (first-user-only). Run `astro dev stop` and delete the DB before a smoke test.
- `:memory:` libsql has one connection. Code inside a transaction MUST use `trx` (`q(s)` in `index.ts`), and hooks MUST call the `cms` they get, or the call blocks or fails with `TRANSACTION_ACTIVE`.
- `JSON.stringify` turns functions in arrays into `null`, so `/schema` strips `hooks` (a field named `hooks` stays, it has a `type`).
- A generic type parameter with a default (`C = {}`) gives context-sensitive functions in the argument that default as their contextual type, so their parameters are implicit `any`. `CmsOptions` intersects `collections` with a plain `Record<string, Collection>` inside `NoInfer` to give inline hooks a contextual type.
- Preset hooks type `data` as `any`. With `Record<string, any>`, a spread with a computed key (`{ ...data, [path]: x }`) is not assignable to a typed collection's `Data`. `collection` MUST stay optional in their argument type (`collection!` in the body); a required one is rejected by `CollectionHooks`.
- Query parsers (`parsePopulate()`, `parseSelect()`) build nested objects from raw query segments. They MUST use `Object.create(null)` nodes: on a plain `{}`, a `__proto__` segment returns `Object.prototype`, and the next write pollutes every object in the process.
- Generic inference skips excess property checks, so `populate` objects need `Exact` to reject unknown keys. For the same reason, type tests of field options use `satisfies Fields`, not `defineCollection()`.
- The recursive read types hit TS2589 on an untyped schema (`{ schema: Schema }`, the admin's client) without the `Wide` guard. `Http` / `HttpFields` in `client.ts` crash vue-tsc with a stack overflow there without their own `string extends keyof` guard.
- `ReadDoc` MUST stay `Simplify<Read<…, S> & SelectedMeta<S>>`, with `Wide` inside `Read`. `Wide<Cs> extends true ? … : Selected<Simplify<Resolve & Meta>, S>` hits TS2589 at `setup(defineCms(…))` in the tests (instantiation limit, with better-auth's types in the same statement), and `Selected<Simplify<Full & Meta>, S>` with `Wide` inside `Full` typechecks but makes tsdown's d.ts build run out of memory (`tsdown --watch` dies with it). Check both `pnpm typecheck` and `tsdown` after changing the read types.
- The client's `findOne` calls `client.find<K, O>(…)` with explicit type arguments; casting the result instead makes TS compare two deferred read types (TS2589). The Nuxt composable passes `options as never` on: TS cannot match its generic `Checked` to the client's, and its own parameter already checks the options.
- `keyof never` is every key, so `Exact<P, never>` would accept any object. `Exact` maps an object under a `true`-only key to `never`; that rejects an object on a relation `populate` does not resolve.
- An empty nested object is sent as the path itself over HTTP: `select: { parent: {} }` is `{ id }` locally but `true` (the whole value) over HTTP. Same for `populate`.
- A dangling relation id reads as `null` with the default populate. Tests that check stored ids MUST read with `populate: false`.
- Kysely 0.29 exports `Migrator` from `kysely/migration`, not from `kysely`.
- zsh: quote paths like `[slug].vue` in shell commands, or the glob silently matches nothing.
- tsdown d.ts output needs explicit types on the Nuxt module (`NuxtModule<Options>`). `@nuxt/schema` must be a peer, or its types get inlined.
- Nitro hook types (`nitro:config`) come from `import type {} from '@nuxt/nitro-server/augments'`.
- Hono `csrf()` only checks form-like content types. JSON requests are protected because browsers preflight them cross-origin and we send no CORS headers.
- TanStack Start throws `multiple entries detected` on a second client entry. `integralAdmin()` sets `isEntry = false` on the admin chunk in `generateBundle`, before Start's post hook reads it.
- `configureServer` also runs during `vite build` (TanStack/Nitro). Check `this.environment.config.command === 'serve'`, not whether a server exists.
- Dev servers bind `[::1]` and `curl localhost` hits them first. Test a production build on `HOST=127.0.0.1` and another port, with its own `DATABASE_URL`, or you test a leftover dev server and write into its DB.
- Browsers compile the HTML `pattern` attribute with the `v` flag, so the server does too. `<textarea>` ignores `pattern`.
- A leftover service worker on `localhost:3000` from another project can hijack navigation. If a page works in incognito but not normally, check DevTools → Application → Service workers.

## Smoke test

```sh
B=localhost:3000; J=/tmp/jar
curl -s -c $J -H 'content-type: application/json' -H "origin: http://$B" \
  -d '{"name":"Admin","email":"a@b.co","password":"password123"}' $B/api/cms/auth/sign-up/email
curl -s -b $J -H 'content-type: application/json' -H "origin: http://$B" \
  -d '{"title":"Hello","slug":"hello"}' $B/api/cms/collections/posts
curl -s $B/
```

Expect 200, 201, and the post in the page HTML. Delete the example's `cms.db` before and after.

## Conventions

- TypeScript strict. Keep the file count small and add no abstraction until a second use exists.
- The local API validates every write with `parseData()`. Every write route MUST stay behind the session middleware. Read routes are public and MUST only accept field names that exist in the schema and that the caller can see (`private`).
- `src/condition.ts` MUST stay free of imports; the admin bundles it.
- Admin UI: plain Vue SFCs with `<script setup>`, Tailwind classes, and the shared `.input` / `.btn` / `.btn-ghost` classes in `style.css`. Host inputs render in the admin's light DOM, so they can use those classes too.
- Versions in use: Astro 7, Nuxt 4.5 (nitropack 2, h3 v1), TanStack Start 1.168 (nitro 3 beta, React 19), Vite 8, TypeScript 6, better-auth 1.7, kysely 0.29, Hono 4, zod 4.
- never mention claude in commits
