# admin

The contract and page runtime of the admin UI and the admin bar, shipped in `dist/admin`. The UI itself is the Vue app in `packages/admin`; its build writes `mount.js` and `bar.js` next to these files. How adapters serve the page (path, favicon, build input, HTML, reference discovery) lives in `src/integrations/admin/`.

## Follow the admin page

The page that `adminHtml()` renders loads:

`entry.ts` → `mountAdmin()` in `mount.js` → `GET /admin-brand` (public) → sign-in → `GET /schema` → `addAdminPages()`

`entry.ts` reads the base path from `data-base`, the favicon from the `__TENON_FAVICON__` define and the browser exports from `#tenon/client-registry`. There is no host options file. The admin shows the login branding from `/admin-brand`; fields and pages arrive in `/schema` after sign-in as a descriptor (`AdminDescriptor`): metadata, `clientRef()` values and a `load: true` flag, never a function.

A field or page with a `load` asks `POST /admin/load` for its data (`load/`). `lazyMount()` (`browser/`) waits for the browser export and the data, passes the result as `ctx.data` and calls `update(ctx)` on refresh. The admin bar gets its items and their data from `GET /admin-bar` (`preview/`), which uses `load/bar-item.ts`.

## Follow a registration

`defineCms({ admin })` and each `plugin.admin` go through `merge/merge-options.ts` once at startup:

`describe/describe-registration.ts` / `describe/describe-bar-item.ts` (validate, split loader from descriptor) → `merge/merge-options.ts` and `merge/merge-bar.ts` (plugins first, then the host; duplicate field or page keys throw; bar items replace by key, and `false` removes one) → `AdminRuntime` on `Core`

Only `AdminRuntime.descriptor` is serialized. The loaders and the actions' `run` and `access` stay in the instance, in `Map`s keyed by registration. A request selects a registration by key; it never names a module or a function.

## Follow an action

`describe/describe-action.ts` checks an action (`label`, exactly one of `run` and an `http(s)` `href`, `confirm` only with `run`, `nav.display` `main` or `content`) and `mergeAdmin()` keeps `run` and `access` in `AdminRuntime.actions`. A link sends its `href` in the descriptor and has no `run`. `create-cms.ts` checks the roles of `access`. `/schema` lists only the actions the caller MAY run (`access/permissions.ts` → `actions/run-action.ts` `visibleActions()`). `POST /admin/actions/:key` (`endpoints/action.endpoint.ts`, behind `session`) calls `runAction()`: 404 for an unknown key or a link, 403 when the rule denies (default admins), then `run({ user, cms })`. A returned text goes back as `message`; a throw is logged and answers 500 with its message, since only allowed users get that far. The admin's `useAction()` asks `confirm` first (`ActionConfirmDialog.vue` in the layout), posts it and shows a toast. Links render as `<a target="_blank">`.

## Follow a load

`POST /admin/load` flows through:

`endpoints/load.endpoint.ts` → `load/load-request.ts` → `load/load.operation.ts` → `load/field-target.ts` / `load/run-loader.ts` / `load/bar-item.ts`

The endpoint checks the body and the session, then builds the caller's local API. `load()` picks the registration by key and runs its loader: a field is checked against the schema first, a page runs as is, a bar item goes through `loadBarItem()`. `run-loader.ts` and `bar-item.ts` check the result with `to-json.ts`.

`tenoncms/admin` is a lightweight entry (`config.ts`): types, `clientRef()` and the text helpers, safe in server and browser code. `tenoncms/admin/mount` is the application renderer. Extensions only use `mount(el, ctx)`, so no framework crosses the boundary. `entry.ts` and the `.d.ts` files are copied to `dist/admin` as is, so they MUST keep their names and stay in this folder. `config.ts`, `vue/vue.ts` and `react/react.ts` are tsdown entries, and the `package.json` exports name their output files. `browser/menu.ts`, `browser/locale.ts` (`ADMIN_LOCALES`, `pickAdminLocale()`, `currentAdminLocale()`), `browser/logo.ts` (`logoAt()`, the logo of one place) and `browser/text.ts` (`translate()`, `translator()`) MUST import only types, because the admin, the admin bar and the site's preview runtime bundle them; `browser/lazy-mount.ts` MUST import only types. Core imports `tenoncms/admin/bar` by its own export and keeps it external in tsdown; tsconfig `paths` and a vitest alias point it at `bar.d.ts`.

## Rules

- `load` runs on the server and MUST only read. Its result MUST be JSON; `to-json.ts` rejects functions, `bigint`, cycles and non-plain objects.
- Loader input comes from the browser. Core validates the shape (`load-request.ts`), looks the registration up with `Map`s, takes field definitions from the schema, and checks that a document ID belongs to the requested collection.
- `/schema` never runs a loader. `/admin-brand` returns branding only. Load responses are `Cache-Control: no-store`.
- The plugin name `admin` is reserved: `/_tenon/admin/load` belongs to this module.

## Rich text extensions

`admin.richtext.extensions` registers a server-safe Tiptap schema with a `clientRef()` browser implementation and optional toolbar controls. The merge retains server extensions separately from the JSON descriptor. See [rich text](../richtext/README.md) for the registration contract and field restrictions.
