# auth

| Path                                    | What it does                                                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `config/options.ts`                     | Host better-auth options, reserving core-owned database, base path, secret and model names.                                    |
| `config/build-options.ts`               | Builds provider options, turns password on unless the host turns it off, and checks sign-up before host hooks.                 |
| `config/sign-in-methods.ts`             | `signInMethods()`: which methods are on; `requireSignInMethod()`: the startup check.                                           |
| `config/email-sign-in.ts`               | `withEmailSender()`: creates a host's `magic-link` or `email-otp` plugin without a sender again, with core's email.            |
| `config/last-passkey.ts`                | `lastPasskey()`: refuses to delete the last passkey while it is the user's only way to sign in.                                |
| `config/last-sign-in-method.ts`         | `lastSignInMethod()`: better-auth's `last-login-method` cookie for password, email OTP, magic link and passkey sign-ins.       |
| `plugins.ts`                            | The `tenoncms/auth` entry: `magicLink()` and `emailOTP()` with optional options and sign-up off.                               |
| `config/user-fields.ts`                 | `userFields`: the validated `language` and `timezone` preferences on the user.                                                 |
| `config/access.ts`                      | `userAccess()`: the `admin()` plugin's permissions per role; only `admin` manages users.                                       |
| `config/last-admin.ts`                  | `lastAdmin()`: a small plugin that refuses `set-role` when no other active admin is left.                                      |
| `config/password-length.ts`             | `passwordLength()`: sign-up's length rules on `/admin/create-user`; `lengthProblem()`.                                         |
| `config/sign-in-user.ts`                | `signInUser()`: server-only `signInUser` and `createSignInLink`, public `GET /sign-in-link?token=`.                            |
| `config/manage-users.ts`                | `manageUsers()`: server-only `listAllUsers`, `deactivateUser`, `reactivateUser`, `removeUserByEmail` for `cms.users`.          |
| `sign-up.ts`                            | `signUpStatus()`: `setup` while no user exists, `signUp` when a visitor MAY sign up.                                           |
| `create-auth.ts`                        | Creates the better-auth provider.                                                                                              |
| `config/base-url.ts`                    | Resolves `auth.baseURL` (else `site.url`), Better Auth's environment URLs, then dynamic development hosts.                     |
| `get-caller.ts`                         | `caller()`: the request's user and preview perspective; a cookie alone grants no drafts.                                       |
| `api-key-caller.ts`                     | `apiKeyCaller()`: verifies an API key and returns `{ id, name, permissions }`.                                                 |
| `config/api-keys.ts`                    | `apiKeys()`: better-auth's `apiKey()`; `apiKeyRoutesOff()` closes its HTTP routes; `newApiKeySecret()` for rolling.            |
| `middleware/api-key.middleware.ts`      | `csrfUnlessApiKey()`; `apiKeyReach()`: behind `session`, a key reaches only `/schema` and, with `backup`, the transfer routes. |
| `middleware/session.middleware.ts`      | `optionalSession()` binds the CMS API to the caller once; `session` requires a session.                                        |
| `middleware/session-hint.middleware.ts` | `sessionHint()`: mirrors the session cookie in the readable `tenon-session` hint cookie.                                       |
| `endpoints/provider.endpoint.ts`        | Delegates GET and POST auth requests to better-auth.                                                                           |
| `endpoints/status.endpoint.ts`          | Public `GET /auth-status`: `signUpStatus()`, `signInMethods()` and the email code length, `no-store`.                          |
| `endpoints/password.endpoint.ts`        | Protected `POST /account/password`: better-auth's server-only `setPassword()`.                                                 |

The provider endpoint runs before core CSRF/session middleware. `caller()` is the only place that turns a request into a user: `optionalSession()`, `cms.withSession()` and the media file routes call it. With `x-api-key` it returns the key as `apiKey` and no user, reading `published`, and throws 401 for a key that is not valid. Without a key or cookie it looks up nothing, and a failed session lookup counts as no user, so public pages keep working with a bad `secret`. Content routes run behind `optionalSession()`; protected feature routes also run behind `session`, which lets a key through to `apiKeyReach()`.

When `email` is configured, `authOptions()` supplies password-reset and verification callbacks through the instance's [email module](../email/README.md). Host callbacks take precedence. Verification requirements and automatic sends stay under the host's Better Auth options.

`signUpStatus()` is the one place that decides whether sign-up is open; the create hook and `/auth-status` both read it. Today `signUp` equals `setup`.

`authOptions(db, secret, host, { email, appName, siteUrl, adminPath, roles })` sets `baseURL` to the host's `auth.baseURL`, else `siteUrl` (the `site.url` origin), and appends better-auth's `admin()` unless a host plugin has the id `admin`: `userAccess(roles)`, `adminRoles: ["admin"]`, `defaultRole: "editor"`. Admins get every user and session permission except impersonation. `lastAdmin()`, `lastPasskey()`, `passwordLength()`, `apiKeyRoutesOff()`, `signInUser()` and `manageUsers()` are always appended; `apiKeys()` unless a host plugin has the id `api-key`. `lastSignInMethod()` is appended unless a host plugin has the id `last-login-method`. It sets the same readable cookie as better-auth's `lastLoginMethod()`, without importing the `better-auth/plugins` barrel, and never stores the method in the database: that would need an endpoint that tells anyone how an email signs in. `deviceAuthorization()` and `bearer()` are appended unless the host has them, for `tenon login`: the client id MUST be `tenon-cli` (`DEVICE_CLIENT_ID`), and the verification page is `${adminPath}/device` in the admin, which signs in first, claims the code (`GET /auth/device`) and approves or denies it. The token the CLI gets is a session token; `bearer()` turns `Authorization: Bearer` into the session cookie, so `caller()` sees a normal session. Without `adminPath` (`admin: false`) there is no page to approve a code on, so `deviceAuthorization()` is not added. A full restore empties the session and device code tables (`transfer/operations/full-tables.ts`). Core's `user.create.before` (`checkCreate()`) runs before the host's: the first user gets `role: "admin"`, even when the host hook returns its own `role`; after that a request needs an admin's session; a call without a request is trusted, which is how invite acceptance and `/setup` create their user. `checkCreate()` reads "no user yet" before the insert, so concurrent creates can both become admin; `setUpFirstAdmin()` serializes its own calls. Only `set-role` needs the last-admin guard: the caller of ban or removal is an active admin, and better-auth refuses both on oneself.

Sign-in methods follow better-auth's options. Password is on unless `emailAndPassword.enabled === false`. Passkey, magic link and email OTP are on with a plugin of id `passkey`, `magic-link` or `email-otp`; `signInMethods()` counts the two email methods only when their plugin has a sender or email is configured. `defineCms()` calls `requireSignInMethod()`: it throws when no method is on, and warns when the only methods are email ones without email. When email is configured, `authOptions()` passes host plugins through `withEmailSender()`. Both better-auth plugins copy their options when created, so it calls the plugin's factory again with the stored `options` plus a sender that renders the `magicLink` or `emailOtp` template. The magic-link sender skips addresses without a user. `lastPasskey()` reads the built options at request time, so it sees those senders.

Passkeys are the host's `passkey()` plugin; core does not bundle `@better-auth/passkey` (an optional peer). `defineCms()` passes `site.name` as the default `appName`, which `passkey()` uses as `rpName`. `/auth-status` reports `password`, `passkeys`, `magicLink`, `emailOtp` and `emailOtpLength` (the plugin's `otpLength`, 6 by default), and the admin shows its passkey UI only when `passkeys` is true. Rate limits default to `storage: "database"`, because serverless instances do not share memory. The returned options keep the host's plugin type: plugin endpoint types can make the declaration build fail (TS7056), so `auth.api` does not type them.

The admin's `/forgot-password` and `/reset-password` screens use Better Auth's request, callback and reset endpoints. The client passes the admin's own reset URL as `redirectTo`, so custom admin paths work. Better Auth validates callback origins, password rules, expiry and single-use tokens. The UI clears the token from the address after success and returns to sign-in.

`sessionHint()` runs on `/auth/*`, before the provider endpoint. It reads the session cookie name from better-auth's
options (`getCookies()`) and compares names without the secure prefix. A set session cookie sets `tenon-session=1`
(not `HttpOnly`, `Lax`, path `/`, `Secure` when the session cookie is); a cleared or expired one clears it. The hint
grants nothing. The site's preview runtime reads it only to decide whether asking for the admin bar is worth a request.

`signInUser()` and `manageUsers()` are core's plugins with endpoints. Server code reaches better-auth's internal adapter only through them, as `ctx.context.internalAdapter`. `signInUser({ userId })` and `createSignInLink({ email })` are `SERVER_ONLY`, so better-call never routes them; call them through `auth.api` with `returnHeaders` to forward the session cookies. A sign-in link token is `newToken()`; the verification table stores `tenon-sign-in:<hashToken(token)>` with the user id, for an hour. `GET /sign-in-link?token=` consumes it (so it works once; an expired value reads as missing), ends all the user's sessions, creates one, sets the cookie and redirects to `callbackURL` (checked with `originCheck`) or `${adminPath}/?settings=security`. A missing, used or expired token redirects to `errorCallbackURL` (also checked) or `${adminPath}/login`, with `?error=INVALID_TOKEN`, like better-auth's magic link. Without `adminPath`, both go to `/`. `users/operations/sign-in-link.operation.ts` builds the link and emails it. `users/operations/create-and-sign-in.operation.ts` calls `signInUser` after creating a user, for invite accept and `POST /setup`.
